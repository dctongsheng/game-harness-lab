# 架构设计：让决策模型成为唯一玩家

日期：2026-10-16。状态：设计提案，尚未实现。来源事实与研究链接见三份 `research-*.md`；本文件规定我们自己的系统如何工作。

## 1. 必须守住的执行边界

“全程由 StartLux Decision 或 Jev 游玩”具体定义为：每个策略目标、动作种类、目标对象及可变执行时长，都必须能追溯到该回合决策模型的有效回答。引擎模拟、碰撞检测、状态测量、固定动作映射不属于策略决策。

| 部件 | 可以做 | 不可以做 |
| --- | --- | --- |
| LLM 教练 | 局前写资料和初版 Harness；局后分析轨迹并提出修改 | 局内看状态后决定下一步；模型超时后代打 |
| 决策模型 | 选择动作、目标、战术阶段、有限记忆更新 | 自行修改环境规则或评测器 |
| 观测与特征层 | 提取位置、可见障碍、距离等事实 | 用搜索器算出最佳动作并只留一个候选 |
| 动作目录 | 枚举接口可接受的动作；拒绝语法或物理接口无效值 | 用“危险”“分数低”等策略判断屏蔽可执行动作 |
| 执行器 | 将模型选择转换为固定按键、方向或固定时长输入 | 自动躲障碍、自动瞄准、自动寻路、按局势分支 |
| 校验器 | 验证 ID、候选集、版本、数值、观测新鲜度 | 替模型选第一个选项或最高启发分选项 |

特别是蛇：若游戏规则禁止立即掉头，适配器可按固定规则表达；但“走这一格会撞墙”是应该让模型判断的风险，不能当成动作无效而偷偷删除。方块的洞数可以作为状态事实，不能由脚本加权后自动决定落点。

V1 的 `strict_model_control` 不允许运行时调用通用 LLM。只给玩家进程决策 API 凭据；教练进程不能连接输入执行通道。每个 `ActionEvent` 必须引用有效的 `DecisionReceipt`，版本及观察序号不符则拒绝执行。

**审计证据不是一句配置声明。** 要检查网络调用日志、全部动作回执与候选集构造；100% 动作有回执仍不足以证明没有作弊，因此还需确认特征 DSL 和固定动作目录没有策略捷径。

## 2. 运行与学习分离

建议模块及职责：

| 模块 | 输入 → 输出 | 是否由 GEPA 修改 |
| --- | --- | --- |
| `GameAdapter` | 引擎状态 → 许可观测；动作 → 引擎变化 | 否，按版本锁定 |
| `GameSpec` | 版本、规则、时钟、观测、得分与终止定义 | 否 |
| `KnowledgeBuilder` | 官方规则、用户材料、攻略 → `GameBrief` | 新资料可生成待审版本；事实不自动覆盖 |
| `HarnessCompiler` | 声明式 Bundle → 经检查的执行配置 | 编译器不能改，Bundle 可改 |
| `DecisionRuntime` | 观测 + Bundle + 局内记忆 → 动作请求 | 运行器不能改 |
| `DecisionProvider` | 内部 Choice 协议 ↔ StartLux / Jev API | 否 |
| `EpisodeRunner` | 固定版本、场景、模型 → 完整轨迹和结果 | 否 |
| `EvolutionWorker` | 局后轨迹 + 历史经验 → GEPA 候选 | 优化提示可版本化；算法配置锁定一轮 |
| `EvaluationService` | 候选和旧版 → 配对成绩、可靠性、延迟 | 评分及门槛不能改 |
| `VersionRegistry` | 候选、证据 → 发布/拒绝/回滚记录 | 否 |

选用 GEPA 的自定义 Adapter 路径。`evaluate` 必须实际运行游戏并调用决策模型；不使用默认“任务模型生成自由文本答案”作为游戏玩家。`make_reflective_dataset` 输出归因清晰的行为证据。GEPA 负责候选反思与搜索，系统自己负责每局任务调度、发布准入、审计和回滚。[GEPA Adapter 源码](https://github.com/gepa-ai/gepa/blob/main/src/gepa/core/adapter.py)

## 3. 初始化：先搞清游戏，再生成 Harness

首次接入不是仅让 LLM 写一段 system prompt，建议按以下顺序：

1. **识别游戏规格。** 确认游戏和引擎版本、模式、可暂停能力、输入动作、得分、结束条件及观察权限。
2. **建立资料包。** 背景、任务目标、规则、常见失败、候选策略、攻略来源分别保存。权威规则是事实，攻略是待验证策略，LLM 推导是待测假设。
3. **检查适用版本。** 例如不同俄罗斯方块的旋转、计分和方块生成机制不同，不能把攻略跨版本直接当规则。
4. **生成声明式 Harness。** 产出决策说明、特征选择、记忆结构、知识摘要和问题模板。必须使用已经批准的动作目录和观测字段。
5. **离线检查。** JSON Schema、字段引用、长度预算、动作目录 ID、没有未授权工具或隐藏策略代码。
6. **建立初始基线。** 首版 H0 的模型、环境、随机种子、时钟、得分规则固定；实际回合确认接口可执行，然后进入进化。

资料分为两种视图：玩家只能接收当前观测权限允许的信息；教练可接收事后诊断证据，但导出的 Harness 不得包含具体测试种子、未来事件序列或隐藏敌人状态。攻略不得成为运行时外部检索后门。

## 4. Harness 的可变与不可变部分

V1 用 GEPA 的文本候选映射，每个键是可独立修改的组件，例如：

```text
decision_instructions   怎样依据当前状态作选择
state_presentation      哪些批准字段先展示、如何表述
feature_spec            从白名单事实运算构建特征的声明
memory_spec             有界记忆字段、窗口和可选阶段
knowledge_summary       已有资料中的策略摘要
```

编译时把这些字符串还原成 Bundle 并校验；失败候选记录编译错误，不运行。游戏得分函数、动作目录、环境源码、种子分割、模型版本、超时策略、评测轮数不在候选里。

**不让 GEPA 首期任意生成 Python。** 生成代码可以把“模型选动作”架空，也会破坏可比性。首期特征语言只允许经过实现审查的只读事实算子；不提供访问环境、网络、时钟、文件或随机数的能力。仅做 AST 检查或限制 Python import 不能视为安全隔离。

后期如需新增特征算子，先作为平台代码变更单独验收，再进入可选算子目录；不把未经审查的代码直接热加载。任意代码实验必须单独标记为扩展轨道，不混入 strict 成绩。

记忆有两层：局内短记忆是近期观测/动作的确定性窗口，或由决策模型选择的有限阶段状态；跨局经验由局后教练总结，随下一版 Bundle 冻结。二者都不能在局内调用 LLM 摘要或重写。

## 5. 一步动作如何发生

```text
observe(revision=t)
  → 取出冻结的策略、合法观测和局内记忆
  → 用固定目录枚举全部可执行动作（不按策略排序截断）
  → provider.decide(state, choice_question, request_id)
  → 校验模型返回、观测序号、动作绑定和截止时间
  → execute(exact_selected_action)
  → 记录环境结果、原始得分和计时
```

StartLux 与 Jev 共用内部 `DecisionRequest/DecisionReceipt`，但分别实现 provider：不假定两者支持相同的控制参数、图像输入、概率字段或 OpenRouter 路径。锁定具体模型版本，`latest` 不用于正式版本对比。

本机现有 StartLux 源码已核查：提供 `POST /v1/systemone`，输入 `state` 和 `questions`，Choice 的 `criteria` 为候选 ID 到说明的映射，返回 `answers` 与 `model`。`think_mode` 是该后端控制项，不盲传给 Jev。本次仅检查源码，没有确认当前服务在线或实际模型延迟。

本机来源：`/Users/biws01/Documents/install_everything/Startlux-decide-inference`，检查时 HEAD `83e5562ddddb88c947055f54e3b89ce662d8770c`；关键文件 `startlux_decide/prompt.py`、`server.py`、`controls.py`。真正接入时再运行健康检查、模型列表与真实 Choice 请求，不能沿用历史性能数字。

无效回答、超时、服务故障：可暂停环境停住状态，在有界预算内重试同一请求；仍失败则标记基础设施失败并结束回合。不能随机走一步、默认选第一项、自动换 LLM。模型给出的低分但有效动作照常执行，低 confidence 不等同错误。

## 6. 每局结束如何优化

首版采用同步状态机：

```text
PLAYING → FINALIZING → OPTIMIZATION_PENDING
        → REFLECTING → CANDIDATE_CHECK → EVALUATING
        → PROMOTED | RETAINED → NEXT_EPISODE

任一步基础设施失败 → FAILED → 有界重试或停在待恢复状态
预算不足 → BUDGET_BLOCKED → 补足预算后恢复原任务
```

- 持久化 `EpisodeResult` 后，以 `game_id + episode_id` 创建唯一优化任务，防重复事件。
- 正常结束、游戏失败、超步数截断都触发反思和候选生成尝试。基础设施失败先归因给服务/环境，不能把断网伪装成策略差。
- 每项任务默认尝试 1–2 个组件修改，必须包含触发本任务的本局反馈，另加历史训练样本；可生成 1–3 个候选，但受显式预算限制。数量为初始提案，不是性能承诺。
- 并非只记住上一局：从训练池采样成功、失败、旧版回归场景，避免灾难性遗忘。
- GEPA 的评测回合与发布评测回合都记轨迹，但属于现有优化任务，不触发新任务。否则一次优化会无限产生更多优化。
- 每局都优化不代表每局都发布。输出可以是“没有合格候选，继续 Hn”；连通性故障或预算耗尽则明确显示等待/失败，不能显示已完成优化。
- 首版预算不足就停止开始下一正式回合，保留待办任务；避免后台无限积压与用户约定失配。

每次任务固定 `dataset_snapshot_id` 和环境版本，并使用独立 `run_dir`；只有恢复同一作业时才能复用 checkpoint。下一局建立新作业，以当前批准版本为种子，外部 Registry 保留血缘。不能随意将新数据塞进旧 checkpoint 后沿用旧评估缓存。实现时固定 GEPA 版本；按该版本配置关闭“满分就跳过反思”，至少尝试一次提案，不能因上一局高分而默默跳过优化。

## 7. 分数、比较和发布

### 成绩不能由优化器改写

持久化两个不同概念：`raw_score` 为游戏原始分数；`objective` 为事先规定的比较指标。若使用归一化，只使用固定常数和固定版本，禁止按当前候选集最大最小值动态缩放。

- 蛇：主要看食物数/环境原分，另报生存步数、碰撞类型；设固定步数上限，禁止单纯活得久刷分。
- 方块：原分、消行数、结束原因；固定计分/旋转/方块分布规则。
- 马里奥：原分单列；任务目标建议按通关率、归一化推进距离、耗时分层比较。刷金币得分与通关能力不能混称为同一个提升。

GEPA 搜索需要标量。马里奥首版可预注册 `10 × I(通关) + clip(最大推进距离 / 固定关卡长度, 0, 1)`，作为候选搜索用分；这是设计提案，未实测。关卡长度来自固定元数据，不由候选推断；发布仍额外要求通关率不退化，不能靠推进分抵消通关能力下降。蛇和方块分别使用上述食物数与消行分，不跨游戏混合。

可将局部奖励、错误原因用于反思；只提高代理奖励、牺牲主指标的版本不发布。模型有效性、基础设施失败率、延迟和成本是额外约束，不与得分随意相加。所有尝试都入账；基础设施故障可标记而非归为撞墙，但不能在候选与旧版之间选择性删掉差结果。

### 四层数据

| 数据层 | 用途 | 对教练可见性 |
| --- | --- | --- |
| training | 生成候选、诊断、失败回放 | 可见 |
| selection validation | GEPA 选优、控制过拟合 | 可反馈；明确它不再是独立测试 |
| promotion panel | 候选与当前版在新场景配对比较 | 不提供轨迹；每批一次性使用，避免反复探测 |
| sealed test | 阶段性报告，冻结版本后一次评估 | 不参与选版或下一轮优化 |

同一版本的两次运行也会有随机差异。新旧版使用相同的一组新种子、同样的预算与模型配置，平衡执行顺序；记录全部逐场分数，不只比较两个最高分。初期可用训练 5–8 场、选优 8 场、发布 32 对场景作为预算起点。发布样本量与最小提升幅度要根据基线方差重新设定，事先固定后再跑，不能边看结果边加场直到显著。

发布应同时满足：控制约束检查通过、主指标达到预注册提升门槛、关键回归指标不超容差、模型输出有效率及延迟符合限制。可用配对差值的区间估计辅助判断；小样本或区间跨零时保留旧版。重复优化会产生自适应选择偏差，即使一次门槛通过也不等于保证泛化。

反复使用相同 holdout 即使只暴露通过/失败也会泄漏选择信息，所以发布面板需轮换或一次性使用。固定回归集合可以长期保留，但只能叫回归检查。封存测试若影响下一版本设计就已被消费，须换新的报告集。

## 8. 版本、审计与故障恢复

版本身份至少绑定：`bundle_hash + game_spec_hash + adapter_commit + knowledge_hash + provider/model_revision + runtime_config_hash + score_version`。StartLux 的 revision 应关联实际权重哈希与加载配置，API 自报名称不能单独证明权重身份。托管后端无法提供不可变 revision 时明确标记证据限制。同样的 Harness 换模型不视为同一版本成绩。

正式回合开局只读一次 active version；中途不热切换。发布用比较交换（expected parent）原子更新活动指针，先写完整制品和证据再更新指针。旧版本永久可追溯。

后台并发是第二阶段能力。较旧任务产出的候选必须重新对比当前 champion，不能覆盖已进化版本。一个游戏/实验通道只有一个发布者；训练任务与玩家可分别限流。

回滚在下一局切换，记录触发原因；版本损坏或违反控制约束可立即终止本局。滚动成绩下降触发复验或暂停，不把不同难度场景的低分直接当成退化。动作执行使用命令序号和一次性回执；重试决策 API 不应重复按键。

轨迹至少记录观测版本、可见状态、全部候选、模型请求/返回、被选择动作、执行回执、原始得分变化、游戏时间、壁钟时间、模型延迟、Bundle 版本和终局原因。日志脱敏，不记录 API 密钥。

## 9. 从可暂停到实时、多角色

暂停模式下，模型等待不推进环境时间；同时统计 `wall_ms`、`game_ticks`、决策 P50/P95/P99。能打通关并不能推出能实时运行。

实时模式增加：观察年龄上限、每动作截止时间、输入持续时间、服务并发限制、时钟漂移与网络抖动测试。过期回答丢弃，不能套用在新局势。输入释放或截止终止属于固定基础设施策略，不计为模型动作；必须单列 missed-decision 指标，不能用脚本补救来维持“全模型控制”的成绩。

任何宏动作只能是模型选定的、固定长度的输入序列。执行器若依据新观察选择分支，就已经成了第二个玩家。蛇默认每格决策；方块先用按键动作，落点选择模式另立 benchmark；马里奥使用“按键组合 × 短固定帧数”，不能直接执行自动过关技能。

王者荣耀阶段可把“选团队战术 → 各英雄选行动 → 选择目标/输入”全部交给决策模型分层完成，LLM 仍只在赛后当教练。层次间的事实交换可以批处理，涉及策略的选择不可硬编码。先证明状态来源、动作权限和延迟足够，再讨论 5v5；可暂停小游戏结果不等价于该阶段可用。
